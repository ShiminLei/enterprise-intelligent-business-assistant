# Enterprise Intelligent Business Assistant 宪法

**适用范围**：本项目是企业级 Java + AI 项目实战营的作业交付物，面向本地演示环境，由单人开发。
以下原则按这一规模制定；如项目转向生产环境，须先修订本宪法。

## Core Principles

### I. 安全与数据隐私（不可妥协）

- 除登录页、登录页所需的静态资源（样式、前端依赖库）和健康检查端点外，所有页面和接口 MUST 在用户登录后才能访问；权限 MUST 在服务端按登录用户的角色校验，
  不得依赖前端或提示词。
- 密码 MUST NOT 以明文保存或输出到日志。
- 密钥（API Key、凭据）MUST NOT 出现在源代码、提交历史、日志、提示词或模型输出中；MUST 通过环境变量注入，
  仓库中只提供配置示例。
- 会修改业务数据的操作 MUST 在用户明确确认后才执行，并记录执行人、时间和操作内容。
- 用户输入和知识库内容 MUST 视为数据而非指令；其中的指令性内容 MUST NOT 绕过权限校验或写操作确认。

理由：即使是演示项目，泄露 API Key、越权修改数据或被提示词注入操纵，都是真实且代价高的问题，
而防范它们的成本很低。

### II. 有据可依、可追溯的 AI

- 涉及业务数据或公司制度的回答 MUST 基于工具结果或知识库检索结果，制度类回答 MUST 标注引用来源。
- 依据不足时，助手 MUST 明确说明，不得编造数据或制度条款。
- 系统提示词和工具描述 MUST 保存在代码仓库中，随代码一起评审和提交；模型名称 MUST 可配置。
- 项目 MUST 维护一个小型评估问题集（覆盖制度问答、数据查询和核心演示用例），在每次演示或交付前运行一次，
  并记录结果；结果明显变差时 MUST 先修复再交付。
- 每次回答 MUST 能追溯到所调用的工具、调用结果摘要和引用的知识来源。

理由：评价重点是「Java 与 AI 能力是否真正结合」。回答可核实、过程可追溯，是证明这一点的关键，
也是排查错误回答的唯一途径。

### III. 测试先行（不可妥协）

- 业务规则和工具 MUST 先写测试再实现（Red-Green-Refactor），至少包括：权限校验、任务状态流转、
  延期判定、各业务工具的输入校验与结果。
- 对外 REST 接口 MUST 有接口测试，覆盖正常、未登录和无权限三类情况。
- 涉及大模型的逻辑 MUST 以确定性方式测试：单元测试和集成测试中 MUST 用 stub 替代真实模型调用，
  测试 MUST 能在没有 API Key 的环境下运行。
- 提交代码前，本地构建命令（编译 + 全部测试）MUST 通过。

理由：借助 AI 编程工具生成代码很快，但也容易悄悄引入错误。先写测试，是确认生成代码真正符合规格的
最低成本手段。

### IV. 可观测性

- 服务 MUST 输出结构化日志，每个请求带唯一的请求 ID，并贯穿该请求中的所有工具调用和模型调用。
- 每次模型调用 MUST 记录模型名称、耗时、Token 用量；每次工具调用 MUST 记录工具名称、耗时和是否成功。
- 日志 MUST 遵守原则 I：不得包含密钥和密码。
- 服务 MUST 提供健康检查端点。

理由：Agent 一次请求会连续调用多个工具和模型，没有日志就无法解释某条回答是怎么得出的，
演示出问题时也无法快速定位。

### V. 简单性

- 只实现满足当前规格说明的最简方案（YAGNI）；不做投机性抽象、插件体系或为假想需求设计的配置。
- 系统 MUST 作为单个可部署应用交付，不拆分微服务。
- 优先使用框架已有能力（Spring Boot、Spring AI / LangChain4j），不自建基础设施。
- 新增第三方依赖、中间件或数据存储 MUST 在 plan 的复杂度追踪中说明理由及被否决的更简单方案。
- MUST 采用单 Agent + 工具调用；MUST NOT 引入多智能体编排。

理由：这是有明确截止时间的单人作业。每多一个组件，都会增加启动失败的风险和演示时需要解释的内容。

## 技术与平台约束

- 后端：Java 21 或更高版本 + Spring Boot 3.x；使用 Maven 或 Gradle 构建，并提交 wrapper。
- 大模型：统一使用阿里云百炼，经 OpenAI 兼容接口调用；对话模型默认 qwen-plus，向量模型为 text-embedding-v4
  （1024 维）。模型调用 MUST 通过统一的抽象层（Spring AI 或 LangChain4j），业务代码不直接依赖具体提供商。
- 全项目只需一个百炼 API Key，通过环境变量注入。
- 前端为简单的 Web 页面，与后端一起打包在同一应用中。
- 数据库结构变更 MUST 通过版本化迁移脚本管理；示例数据 MUST 在首次启动时自动初始化。
- 系统 MUST 能按 README 一键启动（例如 Docker Compose 或单条构建运行命令），除 API Key 外无需手动配置。

## 开发流程与质量门禁

- 每个功能遵循 Spec Kit 流程：specify → clarify（按需）→ plan → tasks → implement。
  plan MUST 包含针对本宪法各原则的 Constitution Check。
- 开发者在每次提交前 MUST 自查是否符合本宪法，重点检查原则 I（密钥、权限、写操作确认）和原则 II（引用来源）。
- 质量门禁：本地构建和全部测试通过；仓库中无真实 API Key；交付前评估问题集已运行并记录结果。
- 交付前 MUST 按 README 在干净环境中完整启动一次，并跑通核心演示用例。

## Governance

- 本宪法优先于其他开发实践和规范；发生冲突时以本宪法为准，直至本宪法被修订。
- 修订本宪法需更新此文件，说明修订理由；如影响已有的 spec、plan 或代码，需同时说明如何调整。
- 版本号遵循语义化版本：
  - MAJOR：以不向后兼容的方式删除或重新定义原则。
  - MINOR：新增原则或章节，或实质性扩充指导内容。
  - PATCH：澄清说明、措辞调整和错别字修正。
- 每个功能的 plan 阶段都需要进行合规审查。任何偏离 MUST 记录在 plan 的复杂度追踪中，并注明理由。
